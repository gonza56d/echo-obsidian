## Gotchas
- **coverage.py JSON `executed_lines` ≠ statements**: it also lists docstrings and excluded lines that ran (`# pragma: no cover`, `if TYPE_CHECKING:`) — ~850 lines on app/. Totals must come from `totals`/`summary`, never from counting the lists (#2550 `46436fb4`).

- **Coverage is not deterministic run to run** (2026-11-06): two runs of identical code differed by 8 lines — random polyfactory data (`notification/service.py` 616/619/695/698 'no recipients' returns, `export/schemas.py` 84 empty description, `export/service.py` 170/251) and timing (`app/database/base.py` 387-392 slow-query log, reached only when the machine is loaded). A strict line diff flaps; hence per-test contexts at the base + attribution + reruns in check_coverage.py.
- **Holding a row from the app engine hides the request (2026-11-06, file 13):** a holder taken with `db.session_factory().get_bind().connect()` and the request's pooled session ended up on the same DBAPI connection: the PATCH blocked in Python on `cursor.execute` and never showed as a second backend in `pg_stat_activity` (the thread stack proved the wait, the catalog showed one backend). A holder on its own `create_engine(postgres_dsn, poolclass=NullPool)` gets its own backend, and the request shows `wait_event_type = 'Lock'` (its `query` column stays stale, `ROLLBACK`; key the poll on the wait, not the text). `pytest @file` reads a list of ids with brackets without shell escaping (reversed-order runs).
- **`UPDATE ... WHERE id IN (SELECT ... LIMIT n FOR UPDATE SKIP LOCKED)` is not bounded by n.** With `reltuples = 0` (the table analyzed while empty: a queue between bursts, or the suite after a module reset) Postgres 16 plans a `Nested Loop Semi Join` with the subquery on the inner side and re-runs it per outer row; each re-run skips the rows the statement already updated, so the LIMIT restarts on the rest (3 claimed with batch_size=1). Every other statistics state tried (fresh, 6, 206, 2,006 rows) ran it once. Select the candidates in a `MATERIALIZED` CTE and join it. A test that guards a bound must `ANALYZE` the empty table first (`analyze_empty_queue`).
- **structlog: configure once per process.** `configure_logging()` hands `structlog.configure` a new processors list; a logger cached on first use (`cache_logger_on_first_use=True`) keeps the old list, so later processor changes (`capture_logs`) never see it. `AccessLoggerMiddleware.__init__` did this per app instance, and `test_user_event_write_path.py` builds one per test; under xdist that module ran before the capture tests on a worker. Found with a throwaway pytest plugin logging `id(structlog.get_config()['processors'])` around every test.
