## Gotchas
- **`UPDATE ... WHERE id IN (SELECT ... LIMIT n FOR UPDATE SKIP LOCKED)` is not bounded by n.** With `reltuples = 0` (the table analyzed while empty: a queue between bursts, or the suite after a module reset) Postgres 16 plans a `Nested Loop Semi Join` with the subquery on the inner side and re-runs it per outer row; each re-run skips the rows the statement already updated, so the LIMIT restarts on the rest (3 claimed with batch_size=1). Every other statistics state tried (fresh, 6, 206, 2,006 rows) ran it once. Select the candidates in a `MATERIALIZED` CTE and join it. A test that guards a bound must `ANALYZE` the empty table first (`analyze_empty_queue`).
- **structlog: configure once per process.** `configure_logging()` hands `structlog.configure` a new processors list; a logger cached on first use (`cache_logger_on_first_use=True`) keeps the old list, so later processor changes (`capture_logs`) never see it. `AccessLoggerMiddleware.__init__` did this per app instance, and `test_user_event_write_path.py` builds one per test; under xdist that module ran before the capture tests on a worker. Found with a throwaway pytest plugin logging `id(structlog.get_config()['processors'])` around every test.
